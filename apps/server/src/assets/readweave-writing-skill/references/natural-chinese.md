# 自然中文参考

## 1. 使用方法

本文件帮助智能体先判断读者场景，再选择中文表达；自然化必须保持主体、动作、对象、否定、条件、范围、可能性、完成状态、数量归属、来源和因果关系

固定处理顺序如下：

- 第一步，确定主要场景和读者需要完成的判断

- 第二步，标记不能改动的代码、命令、路径、接口、字段、枚举、状态码、数字、日期、金额、版本、单位和逐字证据

- 第三步，用语言中立的方式确认谁做什么、对什么做、在什么条件下发生、结果是什么、证据来自哪里

- 第四步，按场景重新组织中文；优先使用明确主体、直接动作和常见搭配

- 第五步，回读事实关系和个人标点；任何关系漂移都使候选文本失败

用户要求一段可以直接使用的成品时，最终回答只保留成品正文；没有明确要求写入文件时不得创建文件，也不得输出临时路径、检查过程或“建议写成”等外层说明

## 2. 场景说明

### 2.1. 聊天回答

- 读者：正在提问并等待直接答复的用户
- 用途：迅速理解发生了什么、为什么以及现在需要做什么
- 语气：直接、克制、允许口语化；用户愤怒时承认具体偏差，不使用客服套话
- 保留项：用户原话中的范围、事实、数字、条件和明确要求
- 高风险表达：完成闭环、进入终态、形成回执、赋能、抓手、机制建设、身份认证式夸奖，以及用“拉长回答”等生硬搭配代替“增加等待时间”或“让回答内容变长”

### 2.2. 状态汇报

- 读者：需要判断进度、问题和下一步的人
- 用途：确认已经完成什么、仍缺什么以及谁继续处理
- 语气：简短、具体、按结果和证据组织
- 保留项：对象名称、完成范围、失败项、检查来源、时间和责任主体
- 高风险表达：任务关闭、结果落盘、状态收口、全链路打通、没有对象的“已完成”、“继续保持”等同义叠加，以及没有新增信息的“明白”“收到”

### 2.3. README

- 读者：第一次进入仓库并判断是否值得使用的人
- 用途：先确认项目用途、适用对象、入口和真实能力，再了解实现与验证
- 语气：清楚、可信、允许必要技术术语
- 保留项：项目名称、安装命令、兼容范围、证据链接、许可证和真实限制
- 高风险表达：底座、闭环、生态、矩阵、统一收口、系统性机制、没有行为说明的能力口号，把 PNG、WebP 等名称留给无法据此判断格式用途的读者，以及“已创建 README”和本机文件路径等交付过程信息

### 2.4. 教程说明

- 读者：第一次执行当前操作的人
- 用途：按顺序完成任务，并知道成功结果和失败后的最小处理动作
- 语气：耐心、直接、一次引入一个新概念
- 保留项：命令、路径、参数、前置条件、操作顺序和可观察结果
- 高风险表达：机械填满固定字段；把简单动作扩展成完整排障手册；只列 npm、JSONL、JSON 等名称却不说明当前命令或数据的实际作用

### 2.5. 架构报告

- 读者：需要审查模块、数据、依赖和取舍的技术人员
- 用途：理解约束如何形成设计，以及设计会改变哪些行为
- 语气：准确、正式、允许成熟行业术语
- 保留项：模块名、接口、数据流、约束、失败行为、证据和未验证部分
- 高风险表达：底座、闭环、收口、证据账本和单任务合同；出现这些抽象词时展开具体入口、返回路径或数据关系；要求只规定携带或复用某个值时，不得自行补充生成主体、生成时间或实现机制

### 2.6. UI 文案

- 读者：不阅读设计文档也要完成操作的用户
- 用途：看懂当前对象、可执行动作、处理结果和恢复办法
- 语气：短、明确、以对象和动作为中心
- 保留项：用户能辨认的对象、真实状态、不可逆后果和必要确认
- 高风险表达：把 TypeScript 类型、API 字段、枚举名或内部状态逐字翻译成导航和按钮；把“标题”“正文”“建议写成”等说明混入可直接显示的文案；使用“删除后将永久删除”等重复动作

### 2.7. API 文档

- 读者：需要正确调用接口并处理失败的开发者
- 用途：确认请求格式、响应语义、状态码、限制和恢复方式
- 语气：精确、稳定、机器名称与中文说明并存
- 保留项：method、path、字段、枚举、状态码、示例值和兼容性约束
- 高风险表达：为追求口语化改变字段含义；把一个英文状态强制映射为唯一中文；不解释 HTTP 状态码、幂等键和决定调用行为的字段；使用“另一份不同的”等重复限定

### 2.8. 审计与事故材料

- 读者：需要核对证据、责任、影响和恢复情况的人
- 用途：确认发生了什么、证据覆盖什么、哪些原因仍未知以及如何恢复
- 语气：正式、克制、区分事实和判断
- 保留项：时间、证据来源、责任主体、影响范围、成熟行业术语、未知信息和恢复动作
- 高风险表达：用闭环、终态、处置完成或安全收口代替具体事故状态；用自然化弱化法律、安全或权限含义；用“不证明生产环境结果”等含混边界代替“不代表生产环境也能达到该目标”；用检查器缺失、文件路径或写作过程代替审计正文

## 3. 上下文术语决策

孤立词语不得直接触发失败；判断依据是所在场景、读者任务和机器含义

- `DeletionReceipt`：代码和 API 保留原名；管理台导航写“数据清理记录”；合规材料在确有证明含义时写“数据删除证明”
- 任务关闭：工单和状态机可以使用；成功执行写“任务完成”；主动撤销写“任务取消”；强制停止写“任务终止”
- 审计日志：安全、数据库和合规文档保留；普通管理界面可以写“审计记录”
- 门禁：真实 CI 阻断条件可以使用；普通说明写“必须通过的检查”或直接说明失败后不会发布
- 闭环：控制理论正式术语可以使用；普通工程说明写明流程从哪里开始、结果返回哪里以及失败如何进入下一轮
- 收口：写明所有请求统一进入哪个入口，或者最后还剩哪项工作
- 终态：状态机文档可以使用；用户界面写“最终状态”或具体结束状态
- 回执：外部系统确实返回确认消息或合规流程生成证明时可以使用；普通列表和导航优先写“记录”“结果”或“证明”

## 4. 翻译腔与内部模型泄漏

以下现象需要结合上下文判断，禁止使用单词替换表直接改写：

- 英文名词链：多个抽象名词连续出现，却没有说明主体、动作和对象
- 无必要名词化：使用“进行验证”“完成分析”“实现提升”代替“验证”“分析”“提高”
- 连接过满：每句话都使用基于、围绕、通过、从而、进而和综上等连接词
- 数据模型泄漏：内部类型、字段或枚举直接决定用户界面的中文名称
- 模板节奏：每段句式和长度高度一致，读者无法分辨重点
- 抽象词堆叠：门禁、闭环、底座、收口、终态和回执连续承担本应展开的实际动作

## 5. 完整解释单元

一个完整解释单元由相邻的一至数句组成，按照下面顺序展开：

- 现象或事件：说明实际发生了什么
- 直接原因：说明现有证据能够确认的形成原因
- 实际结果：说明用户会看到什么或当前操作受到什么影响
- 补充解释或下一步：解释陌生术语、边界和后续动作

前文已经完整说明同一状态时，后文只保留新增信息；例如前文已经写明任务仍在处理中，后文不得再次换词重复最终成功尚未发生

冒号、“例如”“包括”“分为”后面出现两个以上独立项目时换行缩进；项目内部再次出现并列内容时继续增加一级缩进

## 6. 自然度判断边界

确定性检查只能确认标点、标识符、数值、结构和隐私等机械规则；自然度需要结合场景、搭配、事实关系、成对盲评和用户反馈判断

模型评审返回 `PASS` 只能表示当前样本达到既定标准；模型无法确定正确关系时返回 `REVIEW_REQUIRED`，不得自行补造事实；任何事实关系错误都返回 `FAIL`，自然度高分不能覆盖保真失败
